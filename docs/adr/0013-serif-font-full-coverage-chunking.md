# 衬线字体改为热区分片 + 全覆盖尾部，冷传输预算从 423 KB 抬到 1.4 MB

日报页的新闻标题一直是同一行里字重字面不齐。2026-08-01 的三条标题（`[]` 标记的是掉出字体的字）：

```
巴基斯[坦]布[洛]阿特[峰][雪][崩]致3死7失[踪]，[救]援因天气受[阻]
中美俄[太]空攻防战加剧，[卫][星]成现代战争首要目标
西班[牙]批评欧盟部分国家自私回应[休]达移民[危]机
```

`source/news/fonts/noto-serif-sc-700/` 当时是手工裁出的 600 高频汉字子集，`unicode-range` 只覆盖 1214 个码位。落在清单外的字逐字回退到 `--serif` 的下一档，Windows 上即 SimSun；SimSun 没有真粗体，`font-weight:700` 只能靠浏览器合成假粗，于是字重、字面、中宫全对不上。

`readme.md` 当时把这写成主动取舍：「子集外字符回退到系统宋体」。**但取舍的前提站不住。**字表冻结于 2026-07-17 的语料，而新闻标题是开放词表，每天的新事件都在引入未见字。这个洞只会扩大不会收敛——把同一套判据放到 2026-08-01 那天量，全页有 **151** 个字在回退，连站点自己的「驾驶舱」「稍后读」「追踪」「舆论」都在里面。

真正的问题不是「600 字不够」，而是**固定字表和开放词表的结构性错配**。任何固定字表都只是把漏字率变小，改成 3500 字、改成 8105 通用规范汉字表，都只是把同一个洞挪个位置。

## 决定

`tools/generate-news-font.cjs` 把 `subsetRemainChars` 从 `false` 翻成 `true`，并打开 `autoSubset`。`subsets` 仍传字符清单，但语义变了：

- **热区**：`news-serif-sc.txt` 决定首屏分片装什么，取语料中出现过的全部汉字（2605 字符）。
- **尾部**：热区外的**全部字形**保留成自动分片，按 `unicode-range` 命中才下载。

覆盖码位从 1214 涨到 30929，漏字永久归零。`news-serif-sc.txt` 因此从**覆盖契约降级为首屏优化**——它选得好不好只影响冷加载字节数，不再影响正确性，所以语料增长时不需要重新生成。

护栏口径同步改掉。原来的 `transferBytes <= 500_000` 对目录下全部 woff2 求和，分片方案下这个数必然是 13 MB，口径本身失效。新测试解析 `unicode-range`，拿最新一天真正以 `--serif` 渲染的文本算出命中哪几片再求和，卡 1.4 MB；另加一条覆盖断言，直接钉住「一个字都不许掉出去」——那才是本次改动要保住的东西，字节预算只是防退化。

## 代价

**冷加载从 423 KB 涨到约 1.17 MB（2.8 倍）。这是被实测倒逼接受的价格，不是疏忽。**

零漏字做不到与 423 KB 同量级，两个原因都是硬的：

1. **分片开销**：12 MB 的 OTF 切成 309 片后总量变成 13.9 MB。每片都要各带一份字体表，碰几片就付几份开销。
2. **分片按码位排序而非频率**：chunk0 是 U+2CB41 这种生僻扩展区。单日约 500 个去重汉字必然散落到约 40 片，每片 46 KB 里只用到十几个字。

29 天全样本、8 种配置实测（中位冷加载）：

| 配置 | 双字重 | 单字重 700 |
|---|---|---|
| 今天：600 字固定子集 | — | 423 KB（**有漏字**） |
| **热区语料 2605 + 自动尾部（采纳）** | 2131 KB | **1050 KB** |
| 热区 GB2312 7038 + 自动尾部 | 2195 KB | 1081 KB |
| 无热区 · 纯自动分片 | 2809 KB | 1383 KB |
| 热区 + `languageAreas:false` | 2269 KB | 1114 KB |
| 频率三层分档 + 粗尾 | 5220 KB | — |
| 固定字表 2605 · 无尾部 | 5211 KB | — |
| 全字库最粗分片（11 片） | 4904 KB | — |

**这张表要留着。**没有它，下一个人会重走一遍这条路，尤其是"用 `subsets` 做热区"和"频率分层"这两个看起来显然该有效、实测却更差的方向：`subsets` 在 `autoSubset:true` 下会被重切，关掉 `autoSubset` 尾部又粗到 1.1 MB 一片，两头堵死。

## 被否掉的选项

- **扩大固定字表**：只是缩小漏字率，不解决错配。且实测 2605 字无尾部反而要 5211 KB（10 片全命中），比全覆盖方案还差。
- **去掉 webfont，只用系统栈**：零字节、零漏字、渲染绝对一致，但 Windows 上标题变成合成假粗的 SimSun，报刊编辑风的视觉基本没了。
- **可变字体**：CJK VF 体积与 cn-font-split 的支持都不成立。
- **补 400 字重**：冷加载翻倍到 2131 KB，仓库 +26 MB。改为只托管 700，辅助文本移出 `--serif`（见下）。

## Consequences

- **只托管 700 一个字面**，所以 `--serif` 的每一处用法都必须显式写 `font-weight:700`。漏写会静默回退到系统宋体——这正是 `.detail-lede`、`.score-num`、`.mast-issue`、侧栏导航此前的状态。它们已改用正文无衬线栈；`.date-seal`、`.kv b`、`.topic-card b`、`.misses-head h2` 补了显式 700。新增测试「每一处衬线字体用法都显式声明 700 字重」扫描 `news.css` 钉住这条不变量。
- `source/news/fonts/noto-serif-sc-700/` 从 1 个文件变成 325 个 woff2，仓库增量约 13 MB。这是一次性静态资产，不随每日自动提交增长。
- 冷传输预算 1.4 MB 是按实测最大 1198 KB 留约 17% 余量定的。真出现"分片过碎导致命中过多"的退化，测试会抓到。
- 本决策不追认"字体资产可以随便变大"。它划的边界是：**标题渲染正确性优先于首屏字节数**；辅助文本不值得为衬线体付第二份字库。
