# 事件线跨天归并，且身份名取首日标题

档案页把[[事件线]]当历史检索工具用，但登记表里同一件事被切成了多条平行线。抽查 13 条多天事件线，美伊霍尔木兹危机就占了 4 条，日期区间互相重叠——其中两条在同一天各记了一次"新一轮空袭"。想回看这件事，看到的是四个条目，无从判断哪个是要找的、它们什么关系。

碎片化有确定的机制：`match_events_llm` 的 `seen_reg` 限制一个登记事件当天最多被一条精选续接。今天若有两条精选属于同一持续事件，只有一条能续接，另一条被迫新建事件线；新线次日自行吸附新精选，分叉就永久化了。`reconcile_same_day_events` 只作用于同一天的候选事件，从不回头看登记表里的跨天平行线，所以没有任何机制会收敛它们。

另一个独立缺陷是身份名：续接时 `tgt["title"]` 被当天的[[展示标题]]覆盖，所以事件线名实际等于最后一天的新闻标题，每天都在变。检索需要稳定的身份，于是改成**只在首次出现时确定，此后不再覆盖**——当天的标题仍完整记进 history 行，没有信息丢失。

归并复用 `reconcile_same_day_events` 已验证的形状：低频召回键 + 并查集 + 有界批次 + LLM 审计 + 确定性降级。判据写成「是不是同一件事」而非「是不是同一个主体」，因为术语表明确「同一主体的不同事情不算同一条事件线」。

候选门一开始只写了「同类目 + 日期区间重叠」，代码审查时实测发现这等于没有门：一张跨越数周、只有五个类目的登记表里几乎每对线都满足它，408 条中的 406 条会被每天全量送审——22 次额外 LLM 调用、每批失败都把当日质量标记为降级，而且同一批稳定的归档线被反复重判。改成还要求两条线共享至少 8 个低频标题/摘要键后降到约 31 条，且配出来的都是真候选（同一场发布、同一位议员去世的两条线）。阈值由实测标定：真正的碎片线共享 28-46 个键，符合类目与区间条件的噪声对绝大多数只共享 0-3 个。

## Considered Options

- **放开 `seen_reg` 的一对一限制**：改动最小，但只防新增不治存量——已经分叉的四条线依然在那里；且允许多条今日精选涌入同一条线，会让 LLM 更容易把不相关条目塞进热门线。
- **只修身份名，碎片化往后排**：一行改动、风险极低，但检索工具的核心痛点没解决：名字稳定了，四个几乎同名的条目还是四个。
- **合并后重算今天的 `day_count` 与延续判断**：语义上更彻底，但会悄悄推翻连续性门独立验证过的结论（ADR 0002），把可信延续变成归并的副产品。

## Consequences

- **归并只作用于今天没写入的线**。今天的线携带着回填进日报条目的 `event_id` 和连续性门的判定，动它等于重新裁决已验证的结论。今天新建的碎片要等到它不再收到精选的那天才会被并掉——收敛慢一拍，换的是绝不污染当日信任链。
- **审计失败即不合并**，并标记质量降级。取向与 ADR 0004 一致：漏并只是留下两条线，误并毁掉事件身份，不对称就该偏向保守。
- 合并组里以 `first_seen` 最早的那条为身份，`history` 按日期去重、同一天保留身份线自己的那行；`pinned` 与 `active` 只要有一条成立就继承——用户主动标的追踪不能被归并吃掉。
- **存量身份名需要一次性回填**（已执行，408 条中 56 条被覆盖过）。管线只保证今后不再覆盖，旧名字不会自愈。
- 回填有个已知副作用：若某条线的首日行本身是连续性门的假阳性（例如一条美伊线的首日是俄乌空袭），身份名会取到那条错行。这类污染需要"拆线"才能修，归并只会合不会拆，本 ADR 不覆盖。
